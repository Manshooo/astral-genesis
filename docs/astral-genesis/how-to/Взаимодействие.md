# Система интерактивности

Интерактивные объекты в игре строятся на связке трёх вещей: компонент-маркер,
физический слой для луча взаимодействия и метод `interact()` на entity.

## 1. Требования к entity

Entity, с которой должен взаимодействовать игрок, обязана:

1. **Иметь компонент `C_Interactable`** (в `component_resources` в инспекторе,
   либо через `define_components()`).
```gdscript
   @export var action_name: StringName = &"interact"
   @export var prompt_text: String
   @export var enabled: bool = true
   @export var show_key_hint: bool = true
   @export var requires_body: bool = false
```
   `requires_body = true` — физический механизм (рычаг, кнопка): БФЖ бестелесен и
   нажать не может, `S_InteractInput` глотает нажатие, а подсказка объясняет
   «Нужно тело». По умолчанию **false**: двери, порталы и инкубатор обязаны
   работать и у призрака — забег НАЧИНАЕТСЯ развоплощённым и иначе встал бы.
   `enabled = false` временно отключает взаимодействие без удаления компонента —
   но осторожно: выключенный объект `S_InteractionDetector` игнорирует, поэтому он
   не подсвечивается и не показывает подсказку. Если объект должен *объяснить*,
   почему он не работает (запечатанная дверь), оставляйте `enabled = true`, а
   действие пусть отвечает сообщением.
   `show_key_hint = false` убирает из подсказки префикс клавиши — для объектов,
   на которые бессмысленно нажимать («Прохода нет» вместо «[F] Прохода нет»).

2. **Реализовать метод `interact()`**. Его зовёт `S_InteractInput`:
```gdscript
   func interact() -> void:
       UIManager.open_skill_tree(SkillManager, preload("res://data/skill_tree.tres"))
```
   Если метода нет — сработает `assert` в `S_InteractInput.process()`.

   Вызов **отложенный** (`target.interact.call_deferred()`), т.е. тело
   `interact()` выполняется уже вне прохода ECS по сущностям. Так и задумано:
   действия вроде `A_TravelThroughDoor` сносят всю комнату, а `A_FinishRun`
   меняет сцену — делать это в середине итерации нельзя (с GECS v9 системы ходят
   по массивам архетипов zero-copy, см. «Правило v9» в
   [[GECS и правила движка]]). Практическое
   следствие: между нажатием и эффектом проходит кадр, и `interact()` не может
   рассчитывать, что сущность-цель ещё жива — проверяйте `is_instance_valid`,
   если храните ссылки.

3. **Иметь коллайдер на слое `interactives` (layer_4, маска-бит 8)**.
   Луч игрока (`InteractRay`, дочерний узел `Camera3D`) настроен на
   `collision_mask = 8`, то есть попадает только в объекты слоя `interactives`.
   Коллайдер может висеть на самой entity (`use_collision = true` у CSG-нод,
   как у `CSGBox3D`) либо на дочернем `StaticBody3D` (как у инкубатора —
   `Incubator/InteractBody`).

## 2. Как резолвится цель луча

`S_InteractionDetector` каждый кадр кастует луч из `interact_ray` игрока и
поднимается по дереву узлов вверх от коллайдера, пока не найдёт `Entity` с
`C_Interactable`:

```gdscript
func _resolve_interactable(collider: Object) -> Entity:
	var node := collider as Node
	while node:
		if node is Entity and node.has_component(C_Interactable):
			var c := node.get_component(C_Interactable) as C_Interactable
			return node if c.enabled else null
		node = node.get_parent()
	return null
```

Отсюда следствие: **коллайдер не обязан быть на самой Entity** — можно
повесить `StaticBody3D` с `CollisionShape3D` глубоко внутри импортированной
сцены (как в `hub.tscn`), лишь бы где-то выше по иерархии была нода-Entity с
`C_Interactable`.

## 3. Визуальный отклик (крестик + обводка)

Два независимых наблюдателя реагируют на компонент `C_Highlighted`,
который `S_InteractionDetector` вешает/снимает на цель:

- **Прицел (`UI_Crosshair`)** слушает мировые сигналы `component_added` /
  `component_removed` и увеличивается при появлении `C_Highlighted` —
  работает для любой Entity, без требований к типу узла.
- **Обводка (`O_OutlineVisual` + `S_OutlineMask`)** — силуэт, нарисованный
  **постэффектом**, а не материалом на мешах. Наблюдатель переводит **все** меши
  сущности на отдельный слой видимости (`outline_mask`, 20-й — см.
  [[Конвенции проекта]] §2), система рендерит этот слой в маску (`SubViewport` с
  камерой-двойником, у которой `cull_mask` — ровно один бит) и обводит маску
  полноэкранным шейдером `assets/shared/shaders/outline_mask.gdshader`. Цвет и
  толщина — данные: `assets/shared/materials/outline_mask.tres`.

  Отсюда три свойства, которых у прежнего `material_overlay` не было и не могло
  быть внутри того подхода: **толщина задана в пикселях** и не зависит ни от
  размера объекта, ни от расстояния до него, ни от того, плоская у него грань
  или нет; **составной объект даёт ОДИН силуэт** без внутренних рёбер — маска не
  знает, из скольких мешей он собран; и мерцание из §5 ушло вместе с
  overlay-материалом.

  Цена ограничена с двух сторон, потому что полноэкранный проход ради подсветки
  одного объекта — главный риск подхода. Пока ничего не выделено, маска стоит в
  `UPDATE_DISABLED` и не рендерится вовсе. Когда выделено — шейдер гоняется не по
  всему экрану, а по прямоугольнику, в который проецируется габарит объекта (плюс
  запас на толщину); объект, зашедший за камеру, честно обводится по всему
  экрану — `unproject_position` там врёт зеркальной проекцией, и ошибиться в этом
  редком кадре дешевле, чем обрезать контур.

  Где их искать — знает `RS_EntityVisuals.geometries()`: сама entity, если она
  `GeometryInstance3D` (сюда попадают и `MeshInstance3D`, и CSG-примитивы), плюс
  **всё поддерево**, независимо от имён узлов. **Об иерархии думать не нужно** —
  импортированный `.glb`, где сущность `Node3D`, а меши где-то внутри, работает
  сам собой.

  Если геометрии нет вовсе, наблюдатель пишет предупреждение, а не молчит: объект
  интерактивный, но рисовать нечего — это ошибка сцены.

  **Переопределение — `C_VisualRoot { path }`.** Нужно только когда автоматика
  промахивается: в сцене есть меши, которые красить не надо (декор, партиклы),
  или красить надо строго один узел из многих. Путь указывается **относительно
  сущности**; битый путь даёт предупреждение и откат к обычному поиску.

  Тот же `RS_EntityVisuals` использует `O_BodyVisual` (`primary()` — основной меш
  сущности), чтобы правило поиска жило в одном месте и не разъезжалось.

## 3.1. Текстовый отклик: подсказка и экранное сообщение

Два разных канала, не путать:

- **Подсказка (`hud_prompt.gd`)** — постоянная, пока крестик на объекте. Берёт
  `C_Interactable.prompt_text` и, если `show_key_hint`, добавляет клавишу.
  Клавиша **не пишется руками**: она резолвится из `InputMap` по
  `C_Interactable.action_name` через `SettingsManager.action_display_name()`.
  Отсюда два следствия: работает для любого действия (у тела для захвата будет
  «[ЛКМ]», а не «[F]»), и после переназначения подсказка обновляется **на лету** —
  `hud_prompt` подписан на `SettingsManager.settings_changed`.
  Это описание *состояния*: у дверей его проставляет `RunManager` при биндинге
  рёбер — «Пройти» / «Заперто» / «Прохода нет», у порталов «Подняться» /
  «Спуститься»; у механизма с `requires_body` призрак видит «Нужно тело: …».
- **Сообщение (`C_ScreenMessage` → `hud_message.gd`)** — разовая реплика на
  нажатие («Заперто. Нужен ключ доступа к уровню»). Логика вешает компонент на
  игрока, HUD его рисует, `S_ScreenMessage` снимает по таймеру
  (`remaining`) — тот же приём развязки, что `C_Highlighted` → `O_OutlineVisual`.

Показ повторного сообщения делается **remove + add** компонента (см.
`A_TravelThroughDoor._notify`): прямая запись в поля компонента миру не
сигналится, и HUD не узнал бы о новом тексте.

## 4. Чек-лист при добавлении нового интерактивного объекта

- [ ] Entity extends `Entity` (или сцена с рутом-Entity)
- [ ] `C_Interactable` в `component_resources`
- [ ] Реализован `interact()`
- [ ] Коллайдер (сам объект или дочерний `StaticBody3D`) на слое `interactives`
- [ ] Меш — где угодно в поддереве, имя роли не играет. Отдельно про обводку
      думать не нужно; `C_VisualRoot` добавляй, только если красить надо не всё
      (см. §3)

## 5. Возможные проблемы

**Мерцание меша под обводкой — история, а не текущая проблема.** Пока обводка
была `material_overlay` на каждом меше, меш без `material_override` «моргал»:
overlay смешивался с тем, что под ним, — симптом самого подхода. Рецепт был
«поставь на объект хоть какой-нибудь материал». С переездом на маску (§3) причина
исчезла: материалы мешей обводка больше не трогает вовсе, и ставить
`material_override` ради неё не нужно.

**Обводка видна сквозь стены.** Камера маски снимает ТОЛЬКО слой обводки, поэтому
глубина остального мира ей не мешает. На практике это не всплывает: `C_Highlighted`
вешает луч из камеры, то есть только на то, что игрок и так видит. Понадобится
подсветка по площади, а не по лучу — маску придётся сверять с буфером глубины
основного кадра, и это отдельная работа.

**Контура нет вовсе, ошибок тоже.** Первое, что стоит проверить, — слой: любой
посторонний меш, попавший на `outline_mask`, обводится наравне с целью, а маска,
залитая целиком (например, если камере маски досталось окружение с небом),
даёт «контур» рамкой по краю кадра. `dev/outline_mask_check.tscn` сторожит
ровно это.
