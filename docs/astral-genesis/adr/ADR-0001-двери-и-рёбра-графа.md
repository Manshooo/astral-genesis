# ADR-0001: Связь дверей комнаты с рёбрами графа уровня

**Статус:** Предложено
**Дата:** 2026-07-13
**Ответственные:** Янислав (арх./код)

## Контекст

Забег генерируется как граф: `RS_LevelGraph` → узлы `RS_LevelNode`, рёбра
`RS_LevelConnection` (`target_node_id`, `type`, `locked_by`, `depth_delta`,
`one_way`). `RunManager` умеет заспавнить комнату по узлу и телепортнуть игрока
в `SpawnPoint`, но **никак не связывает физические двери комнаты с рёбрами
графа**: `travel_to(node_id)` никто не вызывает, `A_UsePortal.execute()` пуст.

Сейчас в проекте сосуществуют **три несогласованных понятия «дверь»**:

| Понятие | Что это | Где | Проблема |
|---|---|---|---|
| `RS_LevelConnection` | Ребро графа (данные) | генератор | не привязано к сцене |
| `complex_door.tscn` | Дверь-Entity (`E_ComplexDoor`, `C_Interactable`, `actions[]`) | хаб | действие захардкожено на `A_StartNewRun` |
| `RoomDoor` | Пустой `Node3D`-маркер | `Room/Doors/` в комнатах | без логики; вручную перечислен в `C_LevelNode.doors: Array[NodePath]` |

TODO в [`c_level_node.gd`](../../../src/components/level/c_level_node.gd) прямо
фиксирует нерешённость: «как будто дверь должна быть отдельной сущностью… не
знаю как лучше».

**Ядро проблемы — не «нода vs сущность», а рассогласование мощностей.**
Генератор выдаёт узлу **переменное** число рёбер (остовное дерево + доп. рёбра
по `EXTRA_EDGE_RATIO` + вертикальные хабы), а у авторской комнаты **фиксированное**
число физических проёмов. Любое решение обязано отвечать: *какой проём ведёт к
какому ребру* и *что делать, когда числа не совпадают*.

### Требования

1. Взаимодействие с дверью → переход в верный соседний узел (`travel_to`).
2. Учёт `locked_by` (заперто без ключа — переход блокируется + фидбэк).
3. Работает и для рукотворного хаба, и для процедурных комнат.
4. Разъезд «проёмов больше/меньше, чем рёбер» разрешается детерминированно.
5. Возврат: войдя из узла B в узел A, игрок появляется у двери в A, ведущей в B,
   а не в общем `SpawnPoint`.
6. Не ломает существующий паттерн интерактивности (`C_Interactable` + `interact()`).

## Решение

**Именованные дверные слоты + компонент-ребро, штампуемый при спавне.**

1. Каждый проём комнаты — дверь-Entity (наследник `E_InteractableObject`) с
   новым компонентом `C_DoorSlot { slot_id: StringName }`. `slot_id` стабилен в
   пределах префаба (`&"north"`, `&"down_a"` …) и авторится вручную.
2. Пресет комнаты в `RS_RoomPresetLibrary` объявляет свои `slot_id`. Подбор
   пресета под узел требует `preset.slots.size() >= node.connections.size()`
   (это связывает ADR с Фазой 2 — генератор больше не может ставить любой
   префаб на любой узел).
3. `RunManager` при спавне сопоставляет рёбра слотам и **штампует** на каждую
   дверь компонент-ребро `C_DoorPortal { target_node_id, locked_by }`. Лишние
   слоты запечатываются (дверь визуально «заварена», `C_Interactable.enabled = false`).
4. Взаимодействие идёт через `actions[]`: единое действие `A_TravelThroughDoor`
   читает `C_DoorPortal` своей entity → при `locked_by` без ключа даёт фидбэк,
   иначе `RunManager.travel_to(target_node_id)`.
5. Возврат: `RunManager` при входе в узел ищет дверь с `C_DoorPortal.target ==
   предыдущий_узел` и ставит игрока к ней; `SpawnPoint` остаётся фолбэком
   (первый вход в забег).

Это устраняет `RoomDoor`-маркеры и `C_LevelNode.doors: Array[NodePath]` как
отдельную сущность: дверь снова становится обычной interactable-Entity, а связь
с графом живёт в компоненте, а не в ручных `NodePath`.

## Рассмотренные варианты

### Вариант A: Двери по порядку, привязка по индексу
`RunManager` раздаёт `connections[i]` дверям в порядке их обхода в сцене.

| Измерение | Оценка |
|---|---|
| Сложность | Низкая |
| Масштабируемость | Плохая |
| Надёжность | Хрупко: порядок дверей в сцене должен совпадать с порядком рёбер |

**Плюсы:** минимум кода, ничего нового в данных.
**Минусы:** автор комнаты обязан держать порядок дверей == порядку рёбер; при
переменном числе рёбер молча ломается; невозможен осмысленный возврат к «той же»
двери.

### Вариант B: Именованные слоты + подбор пресета по мощности (рекомендуется)
Описан в «Решении».

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Масштабируемость | Хорошая (процедурные комнаты «из коробки») |
| Надёжность | Высокая: явные `slot_id`, проверка `slots >= connections` |

**Плюсы:** дверь = обычная Entity (однородно с ECS); замки/типы живут на
компоненте; корректный возврат; связь с графом декларативна.
**Минусы:** вводит `C_DoorSlot`/`C_DoorPortal`/`A_TravelThroughDoor`; накладывает
ограничение на подбор пресетов (нужно учитывать в Фазе 2).

### Вариант C: Двери инстанцируются в рантайме по «голым» якорям
Комната хранит только пустые якоря; `RunManager` инстанцирует префаб двери в
каждый якорь под нужное ребро.

| Измерение | Оценка |
|---|---|
| Сложность | Средняя-высокая |
| Масштабируемость | Хорошая по числу, но теряется авторский контроль вида |
| Надёжность | Средняя (больше рантайм-логики, сложнее отлаживать в редакторе) |

**Плюсы:** число дверей гибко подгоняется под число рёбер.
**Минусы:** двери не видны в редакторе комнаты (хуже авторинг/арт-проход); та же
проблема «какой якорь какому ребру», просто отложенная; больше рантайм-сборки.

## Анализ компромиссов

Главный компромисс — **где живёт ограничение «проёмов ≥ рёбер»**. A прячет его и
ломается молча. C растворяет в рантайме, жертвуя авторингом и арт-контролем над
тем, как выглядит проём. B делает ограничение **явным и проверяемым** на этапе
подбора пресета — это дороже на старте (нужен слой метаданных о слотах), но
единственный вариант, где рассогласование мощностей ловится детерминированно, а
не всплывает багом посреди забега. Для игры, где комнаты — рукотворный арт с
осмысленной геометрией проёмов, авторский контроль (за B, против C) важнее
рантайм-гибкости числа дверей.

## Последствия

- **Проще:** переход между комнатами становится data-driven; `travel_to`
  наконец вызывается; замки/ключи получают естественный дом (`C_DoorPortal`).
- **Проще:** дверь перестаёт быть особым случаем — это обычная interactable-Entity.
- **Сложнее:** `RS_RoomPresetLibrary` (Фаза 2) обязан знать про слоты и
  фильтровать пресеты по `slots >= connections`; узлы с большим числом рёбер
  требуют «богатых» пресетов, иначе подбор упрётся.
- **Пересмотреть позже:** ключи/инвентарь (`level_access_key`) — этот ADR только
  читает `locked_by`, но не решает, откуда берётся ключ (отдельное решение).
- **Пересмотреть позже:** стриминг соседних комнат — сейчас `RunManager` держит
  одну комнату; `C_DoorPortal` совместим с будущим предзагрузом соседей.
