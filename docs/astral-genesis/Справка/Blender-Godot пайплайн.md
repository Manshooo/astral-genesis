# Пайплайн Blender → Godot: нейминг, экспорт, импорт

> Консолидированная заметка. Собирает вместе: формат/настройки экспорта, конвенции именования, механизм защиты материалов от реимпорта, организацию материалов/анимаций/вариантов, организацию файлов Blender.

## 1. Формат экспорта

**Всегда `.glb`** (glTF Binary), не `.gltf`/`.bin`/текстуры отдельно. Один файл = нечего рассинхронизировать, меньше проблем с путями к текстурам между ОС. `.gltf` (текстовый) — только для отладки/постобработки скриптами, не для доставки в проект.

## 2. Настройки экспорта в Blender (glTF 2.0)

| Секция | Настройка | Значение |
|---|---|---|
| Format | Format | glTF Binary (.glb) |
| Transform | +Y Up | включено |
| Geometry | Apply Modifiers | включено (кроме Armature) |
| Geometry | UVs / Normals / **Tangents** | включено (тангенты обязательны под normal maps) |
| Geometry | Vertex Colors | включено, если используются |
| Shading | Image Format | Automatic |
| Armature | Export Deformation Bones Only | включено, если есть служебные IK/control-кости |
| Animation | Export | включено |
| Animation | **Group by NLA Track** | включено — иначе экспортируется один слитый action вместо отдельных именованных клипов |
| Animation | Export Root Motion | по ситуации (если локомоция идёт через кость) |
| Material | Materials | Export (glTF PBR metallic-roughness) |

Отдельно: если после импорта модель выглядит «прозрачной с двух сторон» — включить **Backface Culling** у материала в Blender и переэкспортировать, а не чинить cull mode в Godot вручную каждый раз.

## 3. Нейминг

### 3.1. Суффиксы-хинты Godot (объекты/меши)

Разделитель `-`/`_`/`$`, регистронезависимо. Подтверждённый минимум (полный список меняется между версиями — сверяться с `Node type customization using name suffixes` в доке под свою версию):

| Суффикс | Эффект |
|---|---|
| `-col` | `ConcavePolygonShape3D`, меш остаётся видимым |
| `-convcolonly` | `ConvexPolygonShape3D`, без визуального меша (под rigid body) |
| `-colonly` | точная коллизия, без визуального меша |
| `-noimp` | объект полностью игнорируется при импорте |

### 3.2. Материалы — самое важное правило пайплайна

Имя материала в Blender = **стабильный, человекочитаемый identifier**, не меняется при перекраске/переносе между файлами. Никаких `Material.001`. Пример: `MAT_metal_gold`, `MAT_glass_clear`, `MAT_gradient_warm`, `building`.

Единственный ключ, по которому автоматика Godot сопоставляет «старый» и «новый» материал при реимпорте — **имя**. Нет стабильного имени → нет автоматической привязки.

Известная ловушка: если имя меша совпадает с именем `.glb`-файла, при реимпорте Godot может добавить суффикс `_2` к узлу, разрывая привязку материала (issue godotengine/godot#112405). Не называть меш так же, как файл.

### 3.3. Общая схема имён (по образцу практики Blender Studio: явные, машиночитаемые идентификаторы)

```
MAT_<категория>_<название>   → MAT_gradient_warm, MAT_metal_brass, MAT_glass_clear
SM_<название>                → статичные меши
SM_<название>_col            → коллизия к нему
SK_<название>                → скелетные меши/персонажи
ANIM_<персонаж>_<действие>   → ANIM_hero_walk, ANIM_hero_interact
```

## 4. Проблема реимпорта и как её решать системно

**Причина**: импортёр Godot (`ResourceImporterScene`) при каждом реимпорте полностью пересобирает сцену из данных glTF. Всё, что настроено вручную в Godot и не вынесено явно из этого процесса — теряется.

**Штатные механизмы и их слабые места**:
- «Keep on Reimport» — известны баги потери материала при реимпорте в рантайме (godotengine/godot#42128) и непередачи параметров из Blender (#15853).
- «Use External Material» — рабочий, но ручной (настраивается на каждый файл в Advanced Import Settings), и не работает для безымянных материалов (#64853) — ещё один довод за правило 3.2.

**Решение, которое масштабируется — автоматическая привязка по имени**:

1. Держать «настоящие» материалы Godot как обычные `.tres` в `res://materials/`, имена файлов = имена материалов в Blender.
2. Написать `EditorScenePostImportPlugin` (или более глубокий `GLTFDocumentExtension` — хук прямо в парсинг glTF, работает и на импорт, и на экспорт, и в рантайме), который на импорте любого `.glb` ищет в `res://materials/` файл с совпадающим именем и подставляет его вместо сгенерированного.
3. Зарегистрировать как дефолтный import-script проекта (Project Settings → Import Defaults → Scene → Import Script) — работает автоматически для всех ассетов.

Минимальный скелет (`EditorScenePostImportPlugin`):

```gdscript
@tool
extends EditorScenePostImportPlugin

const MATERIALS_DIR := "res://materials/"

func _internal_process(category: int, base_node: Node, node: Node, resource: Resource, options: Dictionary) -> void:
    if category != InternalImportCategory.INTERNAL_IMPORT_CATEGORY_MATERIAL:
        return
    var mat := resource as Material
    if mat == null or mat.resource_name.is_empty():
        return
    var candidate := "%s%s.tres" % [MATERIALS_DIR, mat.resource_name]
    if ResourceLoader.exists(candidate):
        set_additional_import_option_replaced_resource(resource, load(candidate))
```

(сверять точные сигнатуры методов с классом `EditorScenePostImportPlugin` под свою версию Godot — принцип стабилен, детали API немного меняются между 4.x минорками).

Механизм работает **на уровне материала-ресурса, а не меша целиком** — меш с двумя материалами (например, `building` + `glass` в разных слотах Blender → два surface в Godot) обрабатывается автоматически, без специального кода: скрипт просто по очереди находит и подменяет оба материала на нём по их собственным именам.

Готовые community-аддоны, которые уже делают то же самое (можно взять за основу вместо написания с нуля): **Blender To Godot 4 Pipeline Addon** (michaeljared) и **GLTF Level Importer** (burning-barb, из коробки заменяет glTF-материалы на Godot-материал с тем же именем).

**Форк движка под это не нужен** — GDScript-аддон (или, при необходимости бо́льшей производительности, GDExtension/C++ без пересборки движка) полностью закрывает задачу через официальные точки расширения (`EditorScenePostImportPlugin`, `GLTFDocumentExtension`, `EditorImportPlugin`).

## 5. Материалы — практика

- **Один материал на много мешей — это нормально и правильно**, никакой уникальности на меш не требуется. Один общий материал `building`, вариативность цвета — через развёртку (UV) в конкретную зону градиентной палитры. В Godot это тоже один переиспользуемый `Material`-ресурс, привязанный по имени (§4).
- **Градиентная/палитровая техника albedo** — известный паттерн (gradient/palette texturing): узкая текстура-палитра с несколькими цветовыми полосами, UV геометрии направляет разные части модели в нужную полосу. Держать 1–2 варианта палитры как отдельные, стабильно именованные Godot-материалы (`MAT_gradient_warm/cold`).
- **Металл** — тот же градиентный albedo + `metallic`/`roughness`, полностью укладывается в стандартный glTF PBR, ничего специального не требуется, кроме именования по правилу 3.2.
- **Стекло — не через glTF.** Godot не рендерит `KHR_materials_transmission`/`KHR_materials_volume` из glTF (у StandardMaterial3D есть своя, отдельная, экранно-пространственная функция Refraction, никак не связанная с данными из Blender). Материал `glass` в Blender — только идентификатор-маркер. Настоящий Godot-шейдер стекла собирается заранее руками в движке и подставляется по имени тем же механизмом §4. Тот же принцип — для любого материала, чьи «интересные» параметры физически не выражаются в glTF PBR.
- **Локальная вариация внутри одной палитры** (лёгкий разный оттенок у конкретного объекта) — через параметр `ShaderMaterial` (`set_shader_parameter()` на конкретном `MeshInstance3D`), а не через создание отдельного файла материала.

## 6. Анимации

- Экспорт: **Group by NLA Track** обязательно (§2) — имя NLA-strip становится именем `Animation`-ресурса в `AnimationPlayer` (`ANIM_hero_walk`, не `NLATrack.001`).
- Переиспользование анимаций между разными персонажами — режим импорта **Animation Library** (Godot 4.3+), требует единой конвенции имён костей между скелетами. Встречаются свежие issue про `couldn't resolve track` при применении общей библиотеки к «чужому» скелету — закладывать время на отладку.
- Известный баг (godotengine/godot#115792): при реимпорте могут «поехать» имена костей в путях треков (суффикс `_2`), анимация молча перестаёт применяться. Профилактика та же, что и с материалами — уникальные предсказуемые имена, не полагаться на авто-суффиксы Blender `.001`.

## 7. Варианты одной геометрии («скины»)

glTF-расширение `KHR_materials_variants` (официальный, предназначенный именно для этого механизм) по имеющимся данным **не реализован нативно в Godot** ни на импорт, ни на экспорт — стоит перепроверять актуальный changelog перед тем, как закладываться на это.

Рабочий Godot-native подход уже сегодня:
1. Геометрия импортируется один раз как обычный `ArrayMesh`/`PackedScene`.
2. Разные варианты — разные `MeshInstance3D` (инстансы), у каждого свой `surface_material_override` (`set_surface_override_material(idx, material)`).
3. Материалы-варианты — обычные `.tres`, подставляемые тем же механизмом §4 по имени.

Git-friendly, не зависит от того, реализует ли Godot `KHR_materials_variants`.

## 8. Организация файлов Blender

**На стороне Godot не важно, из какого `.blend` пришёл материал** — важно только совпадение итогового имени материала в экспортированном glTF с именем внешнего `.tres` (§4). Это снимает давление с решения по структуре файлов — привязка по имени работает одинаково независимо от происхождения файла.

- **Не заводить отдельный `.blend` на каждый объект.** При масштабе соло/маленькой команды разумная гранулярность — по категориям (как уже есть: `environment.blend`, `creatures.blend`). Дробить дальше — только когда конкретный объект реально станет узким местом (например, параллельная работа нескольких людей над одним ассетом).
- **Расшарить текстуру — просто держать её как внешний файл** (не запакованную в `.blend`), путь на диске один и тот же в обеих сценах — правка PNG видна везде сразу, без Blender-side линковки.
- **Расшарить сам материал (node-граф)** между файлами — через Asset Browser + **Link** (не Append): выделенный `materials_lib.blend`, материалы помечены как Asset, из `environment.blend`/`creatures.blend` подключаются со связью Link — правки в библиотеке подтягиваются везде. Оправдано, когда рассинхронизация node-графов между файлами между файлами начинает реально болеть, не раньше.
- Даже без Blender-side линковки два независимых datablock'а с одинаковым именем в разных файлах (например, «building» в обоих) всё равно сойдутся в один и тот же Godot-материал на импорте — потому что подмена идёт по имени (§4), а не по происхождению.
- Развивающаяся фича Blender **Project Setup** (общие project-level настройки/ассеты между файлами) движется в сторону того же паттерна «общая библиотека» — на момент разговора ещё не полностью готова, ждать её ради архитектурного решения не стоит, но направление то же самое.

## 9. Итоговый чек-лист

1. Экспорт — всегда `.glb`, настройки по таблице §2.
2. Нейминг — конвенция §3.3, обязательно стабильные имена материалов (§3.2).
3. Post-import скрипт (`EditorScenePostImportPlugin`/`GLTFDocumentExtension`) — подмена материалов по имени из `res://materials/`, зарегистрирован как дефолтный import-script проекта.
4. Один материал можно и нужно шарить между множеством мешей — не плодить материалы искусственно.
5. Стекло и подобные «не-PBR» материалы — не через glTF, отдельный Godot-шейдер, подставляется по имени.
6. Анимации — экспорт через NLA-strips с осмысленными именами, проверять реимпорт на баг с переименованием костей.
7. Варианты одной геометрии — общий меш + `surface_material_override`, не полагаться на `KHR_materials_variants`.
8. Файлы Blender — по категориям, не по объекту; шаринг текстур через общий путь на диске; шаринг материалов (node-графов) — через Asset Browser + Link, когда/если реально понадобится.
9. Форк Godot и переход на USD — не сейчас, ни то ни другое не оправдано на текущем масштабе проекта.
