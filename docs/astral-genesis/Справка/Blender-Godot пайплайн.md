# Стандарт 3D-ассетов: Blender → Godot

> Как ассет доезжает из Blender в игру: где лежит, как называется, сколько весит, что переживает реимпорт.
> Инструменты на стороне художника: **Blender + Ucupaint** (вместо Substance Painter) + **UV Toolkit**. Стиль — **hand paint**.

## 0. Главное правило

**Единица организации — не объект и не сущность, а текстурный сет (материал).**

Из этого следует всё остальное. Один материал живёт на десятках мешей (§8), один `.blend` отдаёт целую категорию объектов (§13), а текстуры принадлежат материалу, а не двери. Поэтому материалы лежат общим плоским списком, а `.glb` нарезаны по категориям — но ни то, ни другое не по сущностям: попытка сделать `src/entities/complex_door/textures/` разваливается на первом же ассете, который переиспользует ту же текстуру.

Второе правило, ради которого существует половина этого документа: **имя материала — единственный ключ, по которому Godot связывает «то, что пришло из Blender» с «тем, что настроено в движке»** (§8).

## 1. Организация файлов

Граница проходит **между искусством и кодом**, а не между сущностями:

- `assets/` — всё, что вышло из Blender/Krita: `.glb`, текстуры, материалы, извлечённые меши. Бинарники, LFS (§14).
- `src/` — сцены, скрипты, компоненты. Текст, обычный git, раскладка по ролям и префиксам (см. [[Конвенции проекта]]).

**Один ассет — один `.glb` — одна папка.** Godot ждёт от импортируемого `.glb` независимой единицы, и всё, что он вокруг него генерирует (извлечённые меши, при неудачных настройках — текстуры), падает рядом с файлом. Пока в папке лежит ровно один ассет, «рядом» это его собственная папка, а не корень проекта. Категорию и раскладку задаёт профиль экспорта плагина `godot_pipeline` (§8), поэтому руками эти папки не создаются.

Материалы и текстуры **по умолчанию общие на проект**: имя материала — глобально уникальный ключ (§4.2), а палитровый материал живёт на десятках мешей, и один файл под него дешевле, чем разъехавшиеся копии. Но **ассет, доросший до собственного набора карт, держит их у себя** — в подпапках `materials/` и `textures/` рядом со своим `.glb`. Это не вкусовщина: у такого материала ровно один потребитель, и «удалить ассет» или «отдать ассет в другой проект» должно быть одним движением, а не охотой по общим папкам.

Первый такой ассет — дверь: у неё личный `MAT_door` с albedo + ORM + normal, а не UV в полосу палитры.

```
assets/
  materials/                  # MAT_*.tres общих материалов: building, furniture, glass, incubator
  textures/                   # T_*.png общих карт
  shared/
    palette/                  # градиентные палитры
  levels/                     # категория = профиль экспорта плагина
    SM_room_A_1/
      SM_room_A_1.glb         # палитровый: материал общий, своих карт нет
      SM_room_A_1.glb.import
    SM_corridor_A_2/
      ...
  props/
    SM_chair_A/
      SM_chair_A.glb
    interactive/              # проп с геймплейным поведением
      SM_Door/
        SM_Door.glb
        materials/            # MAT_door.tres — личный, потребитель один
        textures/             # T_door_albedo.png, T_door_orm.png, T_door_n.png
  characters/                 # риггованные, с armature

src/entities/door/
  complex_door.tscn           # сцена сущности: логика, коллизии, компоненты
  e_complex_door.gd
  a_travel_through_door.gd
```

**Почему не `src/entities/complex_door/graphics/textures/`** — «папка на сущность» это разумный паттерн для кода, и для `src/` он у нас частично так и работает. Но для арта он ломается сразу по трём швам:

1. Раскладку `assets/` **пишет машина** — плагин экспорта по профилю (§8), а не человек по смыслу. Профиль знает про категорию, но ничего не знает про то, какой сущности в `src/` этот меш достанется, и знать не должен: один и тот же `.glb` может кормить несколько сущностей.
2. Материал шарится (§8). Текстура двери, попавшая на панель стены, обязана иметь один адрес, а не два.
3. `assets/` и `src/` по-разному трекаются в git: LFS-правила и `include_filter` экспорта — путевые (§14). Смешивание бинарного арта с текстовыми скриптами в одном дереве превращает эти правила в набор исключений.

Шов между арт-веткой и код-веткой — **имя материала и имя меша**, не путь в файловой системе.

**Звук в структуру ассета не входит.** Механика просит событие строкой (`event:/walk`), а что прозвучит — решает проект byProd. Папки `sound/` у сущности нет и быть не должно, см. [[Звук]].

## 2. Формат экспорта

**Всегда `.glb`** (glTF Binary), не `.gltf`/`.bin`/текстуры отдельно. Один файл = нечего рассинхронизировать, меньше проблем с путями к текстурам между ОС. `.gltf` (текстовый) — только для отладки/постобработки скриптами, не для доставки в проект.

## 3. Настройки экспорта в Blender (glTF 2.0)

| Секция | Настройка | Значение |
|---|---|---|
| Format | Format | glTF Binary (.glb) |
| Transform | +Y Up | включено |
| Geometry | Apply Modifiers | включено (кроме Armature) |
| Geometry | UVs / Normals / **Tangents** | включено (тангенты обязательны под normal maps) |
| Geometry | Vertex Colors | включено, если используются |
| Shading | Image Format | Automatic |
| Armature | Export Deformation Bones Only | включено, если есть служебные IK/control-кости |
| Animation | Export | включено |
| Animation | **Group by NLA Track** | включено — иначе экспортируется один слитый action вместо отдельных именованных клипов |
| Animation | Export Root Motion | по ситуации (если локомоция идёт через кость) |
| Material | Materials | Export (glTF PBR metallic-roughness) |

Перед экспортом: **применить трансформы** объектов (иначе объект будет странно выделяться в редакторе Godot) и **триангулировать** геометрию (модификатор Triangulate + Apply Modifiers) — Godot всё равно триангулирует, но по своему усмотрению, и результат может отличаться от того, что видел художник.

Отдельно: если после импорта модель выглядит «прозрачной с двух сторон» — включить **Backface Culling** у материала в Blender и переэкспортировать, а не чинить cull mode в Godot вручную каждый раз.

## 4. Нейминг

### 4.1. Суффиксы-хинты Godot (объекты/меши)

Разделитель `-`/`_`/`$`, регистронезависимо. Подтверждённый минимум (полный список меняется между версиями — сверяться с `Node type customization using name suffixes` в доке под свою версию):

| Суффикс | Эффект |
|---|---|
| `-col` | `ConcavePolygonShape3D`, меш остаётся видимым |
| `-convcolonly` | `ConvexPolygonShape3D`, без визуального меша (под rigid body) |
| `-colonly` | точная коллизия, без визуального меша |
| `-noimp` | объект полностью игнорируется при импорте |

### 4.2. Материалы — самое важное имя в пайплайне

Имя материала в Blender = **стабильный, человекочитаемый identifier**, не меняется при перекраске/переносе между файлами. Никаких `Material.001`.

Единственный ключ, по которому автоматика Godot сопоставляет «старый» и «новый» материал при реимпорте — **имя**. Нет стабильного имени → нет автоматической привязки.

Известная ловушка: если имя объекта совпадает с именем `.glb`-файла, Godot дописывает цифру (issue godotengine/godot#112405). Наблюдалось на `SM_Door.glb` с объектом `SM_Door`: **суффикс получает корень сцены**, а не объект — дерево выходит `SM_Door2 → SM_Door`. Не называть объект так же, как файл: файл `SM_Door.glb`, объект внутри — `door_slab`.

Важная оговорка: **материалы от этого больше не страдают**. Пока привязка идёт через `use_external` по имени материала (§8), переименование узла её не касается — материал находится по своему собственному имени, а не по пути к узлу. Ломаются `NodePath` в `.tscn`, которые на этот узел ссылаются, и это по-прежнему причина не давать мешу имя файла.

### 4.3. Схема имён

```
MAT_<название>                   материалы     → MAT_door, MAT_building, MAT_glass, MAT_gradient_warm
T_<материал>_<карта>.png         текстуры      → T_door_albedo.png, T_door_orm.png
SM_<название>                    статичные меши
SM_<название>_col                коллизия к нему
SK_<название>                    скелетные меши/персонажи
ANIM_<персонаж>_<действие>       анимации      → ANIM_hero_walk
```

Допустимые суффиксы карт: `_albedo`, `_orm`, `_n`, `_emission`. Больше суффиксов быть не должно — если появился `_ao`, `_rough` или `_metal` отдельным файлом, значит нарушен §6.

**Категорию в имя материала не пишем.** Материалы лежат одним плоским списком (§1), так что префикс категории не помогает найти файл, зато создаёт ложное ощущение, будто `MAT_prop_door` и `MAT_room_door` — два законных имени. Их не бывает: имя уникально на весь проект. Уточнять имя категорией стоит только чтобы развести реально разные материалы (`MAT_gradient_warm` / `MAT_gradient_cold`).

Имя файла материала = имя материала в Blender: `MAT_door` → `assets/materials/MAT_door.tres`. Это не косметика, это ключ подмены (§8) — и заодно причина, по которой имя обязано быть уникальным на весь проект, а не на категорию.

## 5. Бюджет карт: сколько текстур ассету реально нужно

Hand paint отличается от фотореалистичного PBR тем, что **свет, тень и мелкая форма нарисованы в albedo**, а не вычисляются движком из карт. Полный сет из пяти карт — привычка фотореалистичного пайплайна, и для этого проекта он почти всегда избыточен. Уровень выбирается **осознанно на ассет**, по умолчанию — самый низкий из подходящих:

| Уровень | Карты | Когда |
|---|---|---|
| **0. Палитра** | нет собственных текстур | Массовая геометрия: комнаты, коридоры, стены, простые пропы. Один общий градиентный материал, вариативность — через UV в нужную полосу палитры (§10). **Это дефолт проекта.** |
| **1. Albedo** | `_albedo` | Пропы с собственным лицом. Roughness/metallic — скалярами в материале, не текстурой. |
| **2. + ORM** | `_albedo`, `_orm` | Только если шероховатость **реально меняется по поверхности** (мокрые/ржавые/залакированные участки). Ровная поверхность — это уровень 1 со скаляром. |
| **3. + Normal** | `_albedo`, `_orm`, `_n` | Hero-ассеты, которые игрок разглядывает вплотную и часто. |

Две карты не производятся **никогда**:

- **Отдельный AO.** В hand paint окклюзия нарисована в albedo. Если её всё-таки печём — она идёт в канал R карты ORM (§6), отдельным файлом не бывает.
- **Отдельные metallic и roughness.** Всегда упакованы в ORM (§6).

**`complex_door` — hero-ассет** (игрок смотрит на неё в упор при каждом переходе между комнатами) и единственный в проекте на **уровне 3**: `T_door_albedo` + `T_door_orm` + `T_door_n`, 2048² — то самое «2048 только для hero-ассетов» из §7. Всё остальное сейчас на уровне 0, палитрой. Карты лежат в папке самой двери (§1), а не в общих.

## 6. ORM: три карты в одном файле

AO, roughness и metallic — по одному каналу данных каждая. В отдельных файлах две трети каждого файла пустуют. glTF по спецификации ожидает их **упакованными в одну RGB-текстуру**:

```
R = Occlusion    G = Roughness    B = Metallic
```

Это даёт три текстурных выборки вместо пяти в шейдере, втрое меньше файлов и втрое меньше VRAM на этих данных.

**В Blender/Ucupaint**: Ucupaint умеет складывать результаты запечённых каналов в одно изображение через **custom bake target** — именно для ORM и DirectX-нормалей. Со стороны glTF-экспортёра occlusion подключается через узел **glTF Material Output** (включается в Preferences → Add-ons → glTF 2.0 → Shader Editor Add-On), после чего экспортёр сам упаковывает occlusion/roughness/metallic в один образ, если они ссылаются на одну текстуру.

**В Godot**: движок использует `ORMMaterial3D` — материал именно с этим упакованным слотом. Важная деталь: **glTF-импортёр Godot этого не делает автоматически** — он всегда создаёт `StandardMaterial3D` с раздельными слотами (предложение godotengine/godot#70979 закрыто как not planned). Нас это не задевает: мы всё равно подменяем материал внешним `.tres` по имени (§8), и в этом `.tres` руками стоит `ORMMaterial3D`.

### Промежуточные карты — не мусор, но и не ассет

Ucupaint запекает **каждый включённый канал** отдельным изображением, и отключить это нельзя: `MAT_door Ambient Occlusion`, `Roughness`, `Metallic` — это ровно те входы, из которых custom bake target и собирает `MAT_door_ORM`. Убрать их из запечки значит убрать источник ORM. Настраивать ORM отдельной целью — тоже не обходной путь, а штатный способ: своей упаковки в RGB у Ucupaint нет.

Правильная граница проходит не в Ucupaint, а **на выходе в проект**: промежуточные карты остаются в `.blend`, а в `assets/` уезжают только те четыре, что перечислены в §5 — `_albedo`, `_orm`, `_n`, `_emission`. Одна дверь на семи картах вместо трёх — это +1,7 МБ, и каждая пересохранённая версия оседает в LFS навсегда (§14).

Границу держит плагин: при копировании текстур он **отбрасывает всё, что по суффиксу опознаётся как промежуточное** (`_ao`, `_roughness`, `_metallic`, `_height`), и называет отброшенное в отчёте. Незнакомый суффикс копируется — ошибиться в сторону лишнего файла дешевле, чем потерять карту, — но тоже с упоминанием в отчёте. Отсюда требование к именам: сначала **Rename Textures**, потом экспорт. Карта с именем от Ucupaint (`MAT_door Roughness`) суффикса не имеет и уедет в проект как незнакомая.

Отдельный `T_*_roughness` или `T_*_metallic`, доехавший до `assets/`, — это не «ещё одна карта», а сигнал, что упаковка в ORM не состоялась.

## 7. Настройки импорта текстур в Godot

Godot по умолчанию импортирует картинки под 2D (без мипмапов, lossless). Для 3D это неправильно, и авто-детект («Detect 3D») перенастраивает текстуру только в момент, когда она впервые попала в 3D-сцену. Не полагаться на это — выставить осознанно:

| Карта | Compress Mode | Normal Map | Channel Pack | Mipmaps |
|---|---|---|---|---|
| `_albedo` | VRAM Compressed | Disabled | sRGB Friendly | вкл |
| `_orm` | VRAM Compressed | Disabled | sRGB Friendly | вкл |
| `_n` | VRAM Compressed | **Enabled** | **Optimized** | вкл |

- `Normal Map: Enabled` включает RGTC-сжатие — оно держит нормали заметно лучше обычного, потому что нормали нужны только два канала.
- `Channel Pack: Optimized` разрешает формат RG, если синий канал не используется. У нормалей не используется — можно. **У ORM синий канал это metallic**, поэтому там остаётся `sRGB Friendly`.
- Мипмапы обязательны для всего 3D: без них дальняя геометрия зернит и рендерится медленнее. Плата — примерно +33% памяти на текстуру.
- Если VRAM-сжатие видимо портит конкретную рисованную текстуру (hand paint с крупными плоскими заливками и резкими границами — как раз тот случай, где артефакты блочного сжатия заметны) — переключить **эту** текстуру на Lossless, но только после того, как Detect 3D уже отработал, иначе Godot вернёт VRAM Compressed обратно.

Разрешение — тоже бюджет: 512–1024 для пропов, 2048 только для hero-ассетов. В hand paint читаемость даёт рисунок, а не плотность пикселей.

## 8. Материалы: подмена по имени

### Проблема

Импортёр Godot (`ResourceImporterScene`) при каждом реимпорте **полностью пересобирает** сцену из данных glTF. Всё, что настроено вручную в Godot и не вынесено явно из этого процесса — теряется. Материал переживает реимпорт ровно одним способом: если он лежит отдельным файлом снаружи и импортёр знает, что подставить его вместо сгенерированного.

### Решение — явная ссылка в `.import`; извлечение только как бутстрап

Держится всё на **явной записи в `_subresources`** — она хранится в `.import` и переживает полную пересборку:

```
_subresources={
"materials": {
"MAT_door": {
"use_external/enabled": true,
"use_external/fallback_path": "res://assets/materials/MAT_door.tres",
"use_external/path": "uid://b6ywwwtqrc1m4"
}
}
}
```

Проверено экспериментом: у `SM_shelf_B.glb` удалялась запись из кэша `.godot/imported`, то есть шла настоящая пересборка с нуля — ссылка осталась нетронутой, `.tres` не перезаписался. `res://`-путь движок при первом же импорте сам нормализует в `uid://`, это нормально.

Файлы под ссылки создаёт **`Материалы → Извлечь = Extract Once`**, и только для этого он и нужен. Гарантия «не перезапишет существующий» — не вопрос доверия, в `resource_importer_scene.cpp` это одно условие:

```cpp
if (!FileAccess::exists(file_path) || extract_mat == 2 /*overwrite*/) {
	ResourceSaver::save(mat, file_path);
}
```

**Полагаться на извлечение как на постоянный механизм нельзя.** Измерено на `SM_Door.glb`: ссылки на материал не было, `MAT_door.tres` уже существовал — и извлечение записало `use_external/enabled: true` с **пустыми** `path` и `fallback_path`, а `materials/extract` сбросило в `Keep Internal`. Материал молча свалился во внутренний: он есть, он выглядит правдоподобно, просто это не тот материал, который настраивали. Похоже на баг движка, но полагаться на исправление незачем — явная ссылка нужна всё равно, и с ней извлечение до этого пути просто не доходит.

Остальные следствия:

- Настроенный руками `.tres` (ORM, стекло, шейдер) не тронется никогда, сколько бы раз ни переэкспортировался `.glb`.
- Новый материал из Blender подхватывается почти сам: реимпорт создаёт `.tres`, а ссылку на него дописывает прогон `dev/fix_import_settings.ps1`. Ручной щелчок в Advanced Import Settings не нужен ни для одного материала.
- `Extract and Overwrite` — третье значение того же перечисления — затирает настроенный `.tres` каждым реимпортом. Ставить осознанно и ненадолго, например чтобы пересеять материал после переделки в Blender.

Механизм работает **на уровне материала-ресурса, а не меша целиком**: меш с двумя материалами (`MAT_building` + `MAT_glass` в разных слотах Blender → два surface в Godot) обрабатывается сам, у каждого surface своё имя материала и своя связь.

**Что отвергнуто.** «Keep on Reimport» — известны баги потери материала (godotengine/godot#42128, #15853). Ручной «Use External Material» — рабочий, но настраивается на каждый файл поштучно и не работает для безымянных материалов (#64853), ещё один довод за §4.2. Аддон на `GLTFDocumentExtension` (GLTF Level Importer, Blender To Godot 4 Pipeline) — до 4.5 это был единственный масштабируемый путь, сейчас он дублирует движок. Единственное, чего встроенный механизм не умеет, — работать в рантайме на `.glb`, загруженном на лету; понадобится грузить модели в рантайме — вернуться к этому пункту.

### Настройки импорта, которые это включают

На каждый `.glb`, Import-док, дальше `Reimport`:

| Секция | Настройка | Значение |
|---|---|---|
| Узлы | Тип корня | **`None`** — тело приходит из метаданных объекта (§4.1), а не из типа корня |
| — | `_subresources` → материал → Use External | **обязательно**, с реальным путём — это и есть механизм |
| Материалы | Извлечь | `Extract Once` — только чтобы завести файл новому материалу |
| Материалы | Формат извлечения | `Text (*.tres)` — текстовый ресурс, читаемый в diff'е |
| Материалы | Извлечь путь | `res://assets/materials`; своя категорийная папка — когда ассет дорос до собственных карт (§1) |
| glTF | Обработка встроенных изображений | `Discard All Textures` |
| Скрипт импорта | Путь | `res://addons/godot_pipeline/collision_post_import.gd` — коллизии из метаданных Blender |

**`Тип корня` обязан быть `None`, и это не мелочь.** Задать его — значит попросить Godot сделать корнем импортированной сцены узел этого типа. Профиль «Interactive» ставил `StaticBody3D`, и получалось так: корень — пустой `StaticBody3D` без формы (с предупреждением «этот узел не имеет формы, поэтому не может сталкиваться»), а настоящее тело из метаданных — уровнем ниже. Два тела вместо одного, причём верхнее бесполезно. Пока коллизия приходила суффиксами, `Тип корня` был единственным способом дать ассету тело; с вкладкой Collisions плагина он стал вредным. **Значение живёт в профиле экспорта, а не только в `.import`** — плагин переписывает его при каждом экспорте, так что правится он в настройках профиля, иначе вернётся.

**`Discard All Textures` — не оптимизация, а починка.** Дефолт движка (`Extract Textures`) выкладывает встроенные картинки рядом с `.glb` при каждом реимпорте и пропускает запись только если файл лежит точно по тому же пути с совпавшим md5. Стоит перенести карты в свою папку и настроить материал — и на следующем реимпорте они появляются снова, на старом месте. Именно так в `assets/rooms/` завелись дубликаты карт двери. В этом пайплайне текстуры и так приходят отдельными файлами (§7), встроенных в `.glb` быть не должно вовсе — на стороне Blender это `Image Format: None`.

### Инструмент: `dev/fix_import_settings.ps1`

Настройки лежат в `.import`-файлах, по одному на ассет, и щёлкать их поштучно в редакторе — ровно тот ручной труд, против которого весь этот раздел. Скрипт приводит все `*.glb.import` под `assets/` к таблице выше:

```bash
pwsh dev/fix_import_settings.ps1 -DryRun
pwsh dev/fix_import_settings.ps1
```

Главное, что он делает — **сам проставляет ссылки на внешние материалы**. Имена материалов читаются прямо из glTF-чанка `.glb`; для каждого, у кого нашёлся `.tres` с тем же именем, пишется `use_external` с реальным путём. Пустые и битые ссылки при этом лечатся.

Ищет он **от частного к общему**: `<папка ассета>/materials/<имя>.tres`, потом рядом с `.glb`, потом так же вверх по категориям до `assets/`, и только напоследок общая папка. Иначе личный материал доросшего ассета (§1) считался бы потерянным, а ссылка уехала бы на общую папку, где его нет.

Идемпотентен и **уважает ручные настройки**: непустой `extract_path`, непустой скрипт импорта и ссылка, уже указывающая на существующий файл, не затираются; выбранное вручную `Extract and Overwrite` не понижается. Раздел `"meshes"` в `_subresources` не пересобирается вообще — в нём числа с плавающей точкой, и переписывание текста меняло бы тип параметра (`20.0` → `20`).

Правка `.import` пересборку не запускает — после прогона нужен реимпорт: открыть проект в редакторе либо `--headless --path . --import`. Для **нового** ассета с новым материалом порядок из трёх шагов: экспорт → импорт (движок создаст `.tres`) → прогон скрипта (проставит ссылку) → реимпорт. Скрипт сам перечислит материалы, под которые `.tres` ещё нет.

### Практика материалов

- **Один материал на много мешей — это нормально и правильно**, никакой уникальности на меш не требуется. Один общий материал `MAT_building`, вариативность цвета — через развёртку (UV) в конкретную зону градиентной палитры. В Godot это тоже один переиспользуемый `Material`-ресурс, привязанный по имени.
- **Стекло — не через glTF.** Godot не рендерит `KHR_materials_transmission`/`KHR_materials_volume` из glTF (у `StandardMaterial3D` есть своя, отдельная, экранно-пространственная Refraction, никак не связанная с данными из Blender). Материал `MAT_room_glass` в Blender — только идентификатор-маркер. Настоящий Godot-шейдер стекла собирается заранее руками в движке и подставляется по имени тем же механизмом. Тот же принцип — для любого материала, чьи «интересные» параметры физически не выражаются в glTF PBR.
- **Локальная вариация внутри одной палитры** (лёгкий разный оттенок у конкретного объекта) — через параметр `ShaderMaterial` (`set_shader_parameter()` на конкретном `MeshInstance3D`), а не через создание отдельного файла материала.

## 9. Сцена сущности и безопасность реимпорта

**Правило: всё, что настроено руками, лежит снаружи импортированной ветки.** Реимпорт пересобирает только то, что пришло из `.glb`; остальное он не трогает — если это остальное действительно снаружи.

**Дефолт проекта — инстанс `.glb` дочерним узлом с именем `Visual`.** Это то, во что упирается всё остальное: `assets/` держит обезличенный визуал, `src/` его подтягивает и связывает с системами, и структура сцены сущности не зависит от того, как в этот момент организован `.blend`.

```
Door (Node3D)                            ← скрипт сущности, component_resources, actions
├── Visual                               ← инстанс .glb, «Editable Children» ВЫКЛЮЧЕН
│   └── SM_Door (MeshInstance3D)          ← из импорта, руками не трогаем
├── InteractBody (StaticBody3D)          ← коллизия интеракции, слой interactives
│   └── CollisionShape3D
└── InteractBody2 (StaticBody3D)         ← геймплейная коллизия, BoxShape3D
    └── CollisionShape3D
```

Имя `Visual` — одно на все сущности: `C_VisualRoot` и любой будущий код тогда могут рассчитывать на предсказуемый `NodePath`.

Два требования, нарушение которых ломает не сборку, а поведение:

- **Корень сущности — `Node3D` или его наследник, и стоит он в позиции объекта.** `RS_RoomLayout.door_direction()` определяет, к какой стене прижата дверь, по origin самой сущности; если сдвинуть корень, а визуал оставить на месте, дверь припишется к другой стене. Инстанс `.glb` поэтому держим в локальном нуле.
- **Меш ищется автоматикой, а не по имени узла.** `RS_EntityVisuals.geometries()` обходит всё поддерево с `owned=false` — именно чтобы находить меши внутри инстанцированной сцены. Обводка и подмена облика тела работают через него, так что лишний меш в `.glb` (декор, коллизионная болванка) будет покрашен вместе с остальным — на такой случай есть `C_VisualRoot`.
- **`SpawnPoint` в комнате — прямой ребёнок корня.** `RunManager` берёт его как `room.entity.get_node_or_null(^"SpawnPoint")`, то есть путь ровно в один сегмент. Вложенный глубже — молча не находится, игрок появляется не там. Двери такого ограничения не имеют: `RS_RoomLayout.door_entities()` обходит дерево, а не путь.

Два других способа и когда они уместны:

- **Унаследованная сцена** (`New Inherited Scene` от `.glb`) — единственный способ дотянуться ВНУТРЬ импортированной иерархии: переопределить свойство одного меша, подвесить свет внутрь геометрии. Так сделана `src/levels/hub/hub.tscn` — в геометрию хаба вставлены инкубатор, дверь и скелеты. Плата: узел из базы не удалить, переименование узла в Blender тихо теряет переопределения, структура `src/` следует за `.blend`. Godot 4 этот путь намеренно не продвигает (см. §8).
- **Извлечённый меш** на своём `MeshInstance3D` — минимум узлов, меш шарится как обычный ресурс, годится в `MeshLibrary`. Но теряется всё, что `.glb` принёс кроме меша: коллизия из `-col`, иерархия составного объекта, `AnimationPlayer`. И `.res` **перезаписывается на реимпорте вместе с зашитым материалом**, поэтому материал обязан приходить внешним (§8). Только этому варианту нужен меш отдельным файлом — и тогда `.res` (бинарный) рядом с `.glb`, а не `.tres`: текстовый меш это массив вершин в diff'е.

Остальное — при любом варианте:

- **Никогда не включать «Editable Children» на импортированной ветке** и не править узлы внутри неё. Это ровно тот случай, когда реимпорт молча съедает работу.
- Компоненты GECS, интеракция, звук — **на узлах сцены сущности**, никогда внутри импортированной ветки.
- **Коллизия геометрии всегда приходит из `.glb`** — суффиксом `-col` или метаданными плагина (§4.1). Ради этого пайплайн и затевался: авторить её в Godot руками не нужно, она едет вместе с геометрией и обновляется вместе с ней. Комнаты и коридоры берут `-col` (трисетка по всей комнате), а где трисетка дороже без выигрыша — вкладка Collisions даёт примитив: у `complex_door` это `AnimatableBody3D` + `BoxShape3D`.
- **Держать её в двух местах нельзя.** Суффикс `-col` рядом с настроенным в сцене боксом даст вторую коллизию в том же месте — сборку это не сломает, просто станет тихо тяжелее. Оба раза, когда так получалось (дверь после переезда, дверь после настройки Body в Blender), заметно было только по дереву узлов.
- **Объём взаимодействия — исключение, он остаётся в сцене сущности.** `InteractBody` на слое `interactives` это не коллизия геометрии, а геймплейный объём: он намеренно больше двери (`3.15×4.35×0.69` против `2.71×4.21×0.36`) и подгоняется под ощущение прицеливания, а не под форму меша. Такое правится там, где видно игру, а не реэкспортом из Blender.

## 10. Палитра, атласы, трим-листы

Три техники в порядке предпочтения — берём самую дешёвую, которая закрывает задачу:

1. **Градиентная палитра** (уже в проекте, `assets/shared/palette/`). Узкая текстура с цветовыми полосами, UV геометрии направляет разные части модели в нужную полосу. Один материал на всю массовую геометрию, ноль уникальных текстур, ноль стоимости на новый объект. Держать 1–2 варианта палитры как отдельные стабильно именованные материалы (`MAT_gradient_warm`/`_cold`).
2. **Атлас на группу мелких пропов.** Не по одному сету на кружку, стул и горшок — один сет `T_props_kitchen_albedo` на всю группу, разложенную по одной развёртке. Правило нарезки групп — по месту и по частоте появления, не по типу объекта.
3. **Трим-лист** — для повторяющихся архитектурных деталей (кромки панелей, вентиляция, стыки): полосы деталей в одной текстуре, UV фейсов ездят вдоль нужной полосы. Даёт «сорок модульных мешей на два-три материала».

Собственный текстурный сет объект получает, **только если игрок видит его вплотную и часто**. Дверь — да. Горшок — в атлас.

Важная оговорка: **атлас сам по себе не уменьшает draw calls** — он уменьшает количество материалов и переключений состояния. Слияние геометрии (MultiMesh, объединённые меши) — отдельное решение, и проверять эффект надо профайлером, а не на веру.

## 11. Анимации

- Экспорт: **Group by NLA Track** обязательно (§3) — имя NLA-strip становится именем `Animation`-ресурса в `AnimationPlayer` (`ANIM_hero_walk`, не `NLATrack.001`).
- Переиспользование анимаций между разными персонажами — режим импорта **Animation Library** (Godot 4.3+), требует единой конвенции имён костей между скелетами. Встречаются свежие issue про `couldn't resolve track` при применении общей библиотеки к «чужому» скелету — закладывать время на отладку.
- Известный баг (godotengine/godot#115792): при реимпорте могут «поехать» имена костей в путях треков (суффикс `_2`), анимация молча перестаёт применяться. Профилактика та же, что и с материалами — уникальные предсказуемые имена, не полагаться на авто-суффиксы Blender `.001`.
- Скелет перед экспортом — в rest/T-позу, иначе меш приезжает деформированным.

## 12. Варианты одной геометрии («скины»)

glTF-расширение `KHR_materials_variants` (официальный, предназначенный именно для этого механизм) по имеющимся данным **не реализован нативно в Godot** ни на импорт, ни на экспорт — стоит перепроверять актуальный changelog перед тем, как закладываться на это.

Рабочий Godot-native подход уже сегодня:
1. Геометрия импортируется один раз как обычный `ArrayMesh`/`PackedScene`.
2. Разные варианты — разные `MeshInstance3D` (инстансы), у каждого свой `surface_material_override` (`set_surface_override_material(idx, material)`).
3. Материалы-варианты — обычные `.tres`, подставляемые механизмом §8 по имени.

Git-friendly, не зависит от того, реализует ли Godot `KHR_materials_variants`.

## 13. Организация файлов Blender

**На стороне Godot не важно, из какого `.blend` пришёл материал** — важно только совпадение итогового имени материала в экспортированном glTF с именем внешнего `.tres` (§8). Это снимает давление с решения по структуре файлов.

- **Не заводить отдельный `.blend` на каждый объект.** При масштабе соло/маленькой команды разумная гранулярность — по категориям (как уже есть: `buildings.blend`, `monsters.blend`, `hub.blend`). Дробить дальше — только когда конкретный объект реально станет узким местом (параллельная работа нескольких людей над одним ассетом). Обратное тоже верно: **один `.blend` не означает один `.glb`** — из категорийного файла плагин отдаёт отдельный `.glb` на каждый ассет (§1), так что границы `.blend` в раскладке `assets/` не отражаются вовсе.
- **Расшарить текстуру — просто держать её как внешний файл** (не запакованную в `.blend`), путь на диске один и тот же в обеих сценах — правка PNG видна везде сразу, без Blender-side линковки.
- **Расшарить сам материал (node-граф)** между файлами — через Asset Browser + **Link** (не Append): выделенный `materials_lib.blend`, материалы помечены как Asset, из `buildings.blend`/`monsters.blend` подключаются со связью Link. Оправдано, когда рассинхронизация node-графов между файлами начинает реально болеть, не раньше.
- Даже без Blender-side линковки два независимых datablock'а с одинаковым именем в разных файлах всё равно сойдутся в один и тот же Godot-материал на импорте — потому что подмена идёт по имени (§8), а не по происхождению.
- Развивающаяся фича Blender **Project Setup** движется в сторону того же паттерна «общая библиотека» — ждать её ради архитектурного решения не стоит, но направление то же.

## 14. Git, LFS и размер

`.gitattributes` проекта сейчас держит `*.png` **в обычном git**, не в LFS — это было верно, пока png'шки были иконками. С приходом рисованных текстур это ловушка: hand paint означает десятки итеративных пересохранений одного и того же файла на 1–2 МБ, и **каждое остаётся в истории навсегда**. Репозиторий пухнет необратимо — переписать историю потом дороже, чем настроить правило сейчас.

Правило под текстуры сделано **путевым**, чтобы не тащить в LFS иконки и UI — в `.gitattributes` оно уже есть:

```gitattributes
assets/**/textures/*.png filter=lfs diff=lfs merge=lfs -text
```

Отсюда следует требование к раскладке: **рисованные текстуры кладутся только в папку `textures/`** — общую `assets/textures/` или категорийную `assets/<категория>/textures/` (§1). Оба варианта под правило попадают: `assets/**/textures/` по спецификации gitignore матчит и ноль промежуточных папок. А файл, положенный мимо `textures/`, тихо уедет в обычный git — правило путевое и ничего об этом не скажет. Проверять не глазами, а `git check-attr filter -- <файл>`: ответ `filter: lfs` значит попал, `filter: unspecified` — мимо.

Известное исключение: **градиентная палитра в `assets/shared/palette/` под правило не попадает** и лежит в обычном git. Пока это осознанно — палитра рисуется один раз и почти не пересохраняется, а хвост из её версий в истории короткий. Начнёт переписываться итерациями — переносить в `textures/`, а не расширять правило по расширению. Сейчас у неё вообще две копии в разных папках с разной судьбой в LFS, и это надо свести (§16).

`.gitattributes` действует только на будущие коммиты, поэтому правило и введено сейчас — **до** первого коммита текстур. Задним числом это уже переписывание истории.

Что ещё влияет на вес сборки:
- Уровень бюджета карт (§5) — самый крупный рычаг: ассет уровня 0 весит ноль.
- Разрешение (§7) — 2048² вместо 1024² это вчетверо больше.
- Атласы (§10) — экономят не столько байты, сколько материалы и переключения состояния.
- **Storage compression** на импорте примерно вдвое уменьшает размер файла на диске и в PCK, не трогая занятую после загрузки память.

## 15. Чек-лист ассета

1. Выбран **уровень бюджета карт** (§5) — по умолчанию нулевой, повышать осознанно.
2. Материал назван по §4.3, имя уникально на весь проект и стабильно.
3. Отдельных `_ao`/`_rough`/`_metal` файлов нет — только `_orm` (§6).
4. Экспорт `.glb`, настройки по таблице §3; трансформы применены, меш триангулирован.
5. Имя меша не совпадает с именем `.glb`.
6. `.glb` лежит в своей папке, один ассет на папку (§1).
7. Настройки импорта по таблице §8 — проще всего `pwsh dev/fix_import_settings.ps1`, затем реимпорт. Для нового материала прогон нужен дважды (§8).
8. Визуал в сцену сущности — инстансом с именем `Visual`, «Editable Children» выключен (§9).
9. Текстуры импортированы по таблице §7 (мипмапы включены, у нормали — Normal Map + Optimized).
10. Ручные настройки — снаружи импортированной ветки (§9); коллизия не задублирована суффиксом `-col`.
11. Текстуры попадают под LFS-правило — проверено `git check-attr` (§14).
12. Стекло и прочие «не-PBR» материалы — отдельный Godot-шейдер по имени, не через glTF (§8).

## 16. Что осталось сделать в проекте

Стандарт описывает целевое состояние; сейчас не хватает:

1. **Легаси-материалы в `assets/shared/materials/` не по конвенции** — `door.tres`, `outline*.tres`, `portal_*.tres`, `palette_1_(alive).tres`. Переименовать в `MAT_*` синхронно с именами в `.blend` (иначе подмена не найдёт пару), скобки и пробелы убрать. Материалы в `assets/materials/` уже приведены.
2. **Палитра лежит в двух местах** — `assets/shared/palette/Gradient Pallete.png` и `assets/textures/Gradient Pallete.png`, файлы байт в байт одинаковые, но с разными uid, поэтому в память грузятся как два ресурса. `MAT_building` смотрит на вторую, `MAT_furniture` и `palette_1_(alive)` — на первую. Свести в одну, и выбор не праздный: `assets/textures/` попадает под LFS-правило, а `assets/shared/palette/` нет (§14). Либо палитра переезжает в `textures/`, либо правило перестаёт быть чисто путевым.
3. **Объекты названы как файлы** — `SM_Door.glb` содержит объект `SM_Door`, из-за чего корень импортированной сцены зовётся `SM_Door2` (§4.2). Внутри сцены сущности это не видно: узел-инстанс всё равно переименован в `Visual`. Но правило есть правило, и там, где ассет инстанцируют напрямую, имя всплывёт.
4. **`Тип корня` в профиле «Interactive» — поправить на `None`.** В `.import` двери он уже убран, но профиль экспорта всё ещё держит `StaticBody3D` и вернёт его при следующем экспорте (§8). Настройки плагина → профиль «Interactive» → Root Type.
5. **Сцены тел не грузятся.** `e_body_crawler/hound/walker.tscn` ссылаются на удалённые `assets/monsters/models/*.res` из монолитного `monsters.glb`. `body_form_check` падает шестью ассертами «нет облика». Нарезать тела по ассету и перевести сцены по образцу комнат.
6. **`room_template.tscn` учит старому паттерну** — в нём пустой `MeshInstance3D` под меш. Визуал теперь приходит инстансом `.glb` с именем `Visual` (§9), и заглушку под меш держать незачем.
7. **Ни один пресет не выставляет `room_type`** в `data/room_preset_library.tres`, поэтому `room_types_check` падает на «ни одной комнаты с типом», а `gen_verifier` печатает «11 в каталоге, 0 встретилось». К пайплайну ассетов отношения не имеет, но висит рядом.
