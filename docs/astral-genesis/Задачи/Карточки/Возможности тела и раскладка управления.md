# Возможности тела и раскладка управления

Целевая версия: **v0.5.0** (может уехать в v0.6.0 — объём зависит от того,
сколько систем движения придётся разнести).

## Проблема

Что игрок умеет — зависит от того, в чём он сидит. Уже сейчас:

- **БФЖ** летает, проходит сквозь `permeable`, **не прыгает** (прыгать нечем);
- **тело** ходит, прыгает, может жать рычаги (`requires_body`).

Дальше будет хуже: есть 3D-ассет тела **без ног** — туловище с руками. Оно
физически не может прыгать, а может, наоборот, что-то своё. То есть у разных тел
**разные наборы возможностей и, как следствие, разные раскладки управления**.

Сейчас это ветка `if/else` по `C_Embodied` внутри `S_PlayerMovement`. Для двух
состояний терпимо, для набора тел — нет: каждое новое тело добавляет условий в
одну и ту же функцию, а UI управления вообще не знает, что доступно прямо сейчас.

## Предлагаемый паттерн: возможность = компонент

**Наличие компонента = наличие возможности. Отсутствие = её нет.** Безногое тело
просто не несёт `C_Jump` — и никакой системе не нужно про него знать.

```
C_Jump      { velocity }            — умеет прыгать, и на сколько
C_Walk      { speed }               — ходит по земле
C_Flight    { acceleration, ... }   — свободный полёт (это про БФЖ)
C_Phasing   {}                      — проходит сквозь permeable
```

Почему компоненты, а не флаги/битмаска в одном `C_BodyStats`:

- **Запросы вместо условий.** `S_Jump` объявляет `q.with_all([C_PlayerInput,
  C_Jump])` — тело без `C_Jump` в выборку просто не попадает. Ветвлений нет,
  систему прыжка можно писать, не зная о существовании безногих тел.
- **Данные едут вместе с возможностью.** Высота прыжка у каждого тела своя, и
  ей место ровно там же, где сам факт «умеет прыгать».
- **Модульность.** Новая возможность = новый компонент + своя система. Ни один
  существующий файл не правится — это и есть требование «сделать модульно».

Это не противоречит заметке «state machine в ECS — осторожно» из `CLAUDE.md`.
Та про **взаимоисключающие состояния**, которые меняются каждый кадр. Здесь набор
стабилен (меняется только при вселении) и реально меняет **набор запросов** — то
самое исключение, которое заметка и разрешает.

## Передача возможностей при вселении

Обобщение того, что уже сделано для визуала (`C_BodyVisual`).

Все такие компоненты наследуют общий базовый — назовём `C_BodyAbility`. Тогда
`S_BodySnatch._embody` **не перечисляет их поимённо**, а переносит на рига все
компоненты тела, унаследованные от базового; `O_ExpelFromBody` симметрично
снимает. Добавить новую возможность = создать один скрипт, править систему
захвата не нужно.

Что важно не сломать:

- **Свои возможности души** (`C_Flight`, `C_Phasing`) не должны затираться при
  вселении. Варианты: помечать их отдельной базой и «усыплять» на время
  воплощения, либо хранить и восстанавливать так же, как `C_BodyVisual` хранит
  `restore_*`. Решить при реализации.
- **Коалесцирование буфера команд.** remove+add одного типа схлопывается в один
  переезд архетипа, и наблюдатель может не увидеть снятие — на этом уже обожглись
  в [[Визуал захваченного тела]]. Пересадка из тела в тело обязана быть в тестах.

## Раскладка управления

Возможность знает, **каким действием** она вызывается:

```
C_Jump { action_name = &"jump", velocity }
```

Отсюда бесплатно получается то, чего сейчас нет:

- **Подсказки и онбординг** перечисляют не «все действия игры», а те, что
  доступны в текущем теле: HUD спрашивает у рига его `C_BodyAbility`-компоненты и
  показывает их `action_name` через уже готовый
  `SettingsManager.action_display_name()` (тот же приём, что в подсказках
  интерактивов).
- **Ребайндинг не трогаем.** `SettingsManager.REBINDABLE_ACTIONS` остаётся
  объединением всех действий: игрок настраивает **клавишу**, а не возможность.
  Клавиша прыжка остаётся собой, даже когда прыгать нечем.
- **Нажатие недоступного действия** — повод для обратной связи, а не тишины (ср.
  `requires_body` у интерактивов: «Нужно тело»). Например «Этому телу нечем
  прыгать».

## Связь с соседними задачами

- [[Модификаторы механик через скиллы]] — **делать раньше**. Числа возможностей
  (высота прыжка, скорость) обязаны проходить через паттерн модификаторов, иначе
  скилл «+20% к высоте прыжка» снова придётся вшивать руками.
- [[Характеристики захватываемых тел]] — та же ось: там *статы* тела, здесь
  *умения*. Возможно, это одна задача в двух карточках; при реализации
  посмотреть, не сливаются ли модели.
- `C_Interactable.requires_body` — уже существующая половина той же идеи, только
  со стороны интерактивов. Стоит свести к общему виду.

## Объём работ

- `S_PlayerMovement` разъезжается на системы по возможностям (ходьба, прыжок,
  полёт). Это главная часть и главный риск: он сейчас единственная точка, где
  считается скорость игрока.
- `_embody`/`_expel` — обобщённый перенос компонентов.
- HUD/онбординг — показ доступной раскладки.
- Тела-ассеты получают свои наборы (в т.ч. безногое — без `C_Jump`).
