# Возможности тела и раскладка управления

Целевая версия: **v0.5.0**. Статус: **сделано целиком**, ждёт живого прогона.

## Проблема

Что игрок умеет — зависит от того, в чём он сидит. Уже сейчас:

- **БФЖ** летает, проходит сквозь `permeable`, **не прыгает** (прыгать нечем);
- **тело** ходит, прыгает, может жать рычаги (`requires_body`).

Дальше будет хуже: есть 3D-ассет тела **без ног** — туловище с руками. Оно
физически не может прыгать, а может, наоборот, что-то своё. То есть у разных тел
**разные наборы возможностей и, как следствие, разные раскладки управления**.

Было это веткой `if/else` по `C_Embodied` внутри `S_PlayerMovement`. Для двух
состояний терпимо, для набора тел — нет: каждое новое тело добавляет условий в
одну и ту же функцию, а UI управления вообще не знает, что доступно прямо сейчас.

> [!info] Половина модели уже сделана в [[Характеристики захватываемых тел]]
> Паттерн «возможность = компонент» и общий перенос по базовому классу **введены
> и работают**: базовый класс называется `C_BodyTrait`, от него наследуют
> `C_Walk { speed }`, `C_Jump { velocity }`, `C_BodyDecay`; `S_BodySnatch`
> переносит на душу все трейты тела не перечисляя их, `O_ExpelFromBody` снимает,
> `RunManager._restore_embodiment` восстанавливает из сцены — тем же механизмом.
> Тело без `C_Jump` уже не прыгает.
>
> **Что сделано:**
> 1. ~~Разнести `S_PlayerMovement` на системы по возможностям.~~ `S_Phasing`,
>    `S_Gravity`, `S_Walk`, `S_Jump`, `S_Flight`. Ветвлений по `C_Embodied` в
>    движении не осталось ни одного — см. [[#Как разнесли]].
> 2. ~~Возможности **самой души** (`C_Flight`, `C_Phasing`).~~ Базовый класс
>    `C_SoulTrait`, компоненты авторены в сцене души, числа полёта уехали из

## Предлагаемый паттерн: возможность = компонент

**Наличие компонента = наличие возможности. Отсутствие = её нет.** Безногое тело
просто не несёт `C_Jump` — и никакой системе не нужно про него знать.

```
C_Jump      { velocity }            — умеет прыгать, и на сколько
C_Walk      { speed }               — ходит по земле
C_Flight    { acceleration, ... }   — свободный полёт (это про БФЖ)
C_Phasing   {}                      — проходит сквозь permeable
```

Почему компоненты, а не флаги/битмаска в одном «листе характеристик»:

- **Запросы вместо условий.** `S_Jump` объявляет `q.with_all([C_PlayerInput,
  C_Jump])` — тело без `C_Jump` в выборку просто не попадает. Ветвлений нет,
  систему прыжка можно писать, не зная о существовании безногих тел.
- **Данные едут вместе с возможностью.** Высота прыжка у каждого тела своя, и
  ей место ровно там же, где сам факт «умеет прыгать».
- **Модульность.** Новая возможность = новый компонент + своя система. Ни один
  существующий файл не правится — это и есть требование «сделать модульно».

Это не противоречит заметке «state machine в ECS — осторожно» из [[GECS и правила движка]].
Та про **взаимоисключающие состояния**, которые меняются каждый кадр. Здесь набор
стабилен (меняется только при вселении) и реально меняет **набор запросов** — то
самое исключение, которое заметка и разрешает.

## Передача возможностей при вселении

Обобщение того, что уже сделано для визуала (`C_BodyVisual`).

Все такие компоненты наследуют общий базовый — он **уже введён** и называется
`C_BodyTrait` (см. врезку выше). `S_BodySnatch._embody` **не перечисляет их
поимённо**, а переносит на рига все компоненты тела, унаследованные от базового;
`O_ExpelFromBody` симметрично снимает. Добавить новую возможность = создать один
скрипт, править систему захвата не нужно.

Что важно не сломать:

- **Свои возможности души** (`C_Flight`, `C_Phasing`) не должны затираться при
  вселении. Варианты: помечать их отдельной базой и «усыплять» на время
  воплощения, либо хранить и восстанавливать так же, как `C_BodyVisual` хранит
  `restore_*`. Решить при реализации.
- **Коалесцирование буфера команд.** remove+add одного типа схлопывается в один
  переезд архетипа, и наблюдатель может не увидеть снятие — на этом уже обожглись
  в [[Визуал захваченного тела]]. Пересадка из тела в тело обязана быть в тестах.

## Раскладка управления

Возможность знает, **каким действием** она вызывается:

```
C_Jump { action_name = &"jump", velocity }
```

Отсюда бесплатно получается то, чего сейчас нет:

- **Подсказки и онбординг** перечисляют не «все действия игры», а те, что
  доступны в текущем теле: HUD спрашивает у рига его `C_BodyAbility`-компоненты и
  показывает их `action_name` через уже готовый
  `SettingsManager.action_display_name()` (тот же приём, что в подсказках
  интерактивов).
- **Ребайндинг не трогаем.** `SettingsManager.REBINDABLE_ACTIONS` остаётся
  объединением всех действий: игрок настраивает **клавишу**, а не возможность.
  Клавиша прыжка остаётся собой, даже когда прыгать нечем.
- **Нажатие недоступного действия** — повод для обратной связи, а не тишины (ср.
  `requires_body` у интерактивов: «Нужно тело»). Например «Этому телу нечем
  прыгать».

## Как разнесли

Пять систем в группе `"physics"`, каждая — про одну возможность. Тело без
компонента в выборку не попадает, и знать о безногих телах ни одной из них не
нужно.

| Система | Кого забирает | Почему так |
|---|---|---|
| `S_Phasing` | `C_Phasing` / всё остальное | маска — состояние узла, а не компонента |
| `S_Gravity` | `C_Velocity` без `C_Flight` | «падает всё, что не летит» |
| `S_Walk` | `C_Walk` | базис САМОЙ сущности: ходят ногами, не взглядом |
| `S_Jump` | `C_Jump` / всё остальное | защёлку обязан гасить и тот, кому нечем |
| `S_Flight` | `C_Flight` | базис КАМЕРЫ и инерция — смысл механики, не настройка |

**Гравитация выражена отсутствием полёта**, а не собственным компонентом
«невесомость»: второй способ сказать то же самое разошёлся бы с первым, и первый
же случай, когда их забыли согласовать, дал бы летающего и одновременно
падающего игрока.

**Две выборки у `S_Phasing` и `S_Jump`** (`sub_systems()`) — не симметрия ради
симметрии. Маску можно удержать верной только повторным утверждением: наблюдатель
поставил бы её один раз на событие и молча разошёлся бы с истиной при первом же
стороннем изменении. А `jump_pressed` — защёлка, и гасить её обязан в том числе
тот, кому прыгать нечем, иначе нажатие, сделанное призраком, срабатывает в тот
самый миг, когда он вселяется в прыгучее тело. Обе половины правила держатся в
одном файле: разнеси их — и «кто ставит бит обратно» станет вопросом порядка
систем.

## HUD-раскладка

Панель `UI_HudAbilities` (`src/ui/hud/hud_abilities.gd`, узел `Hud/AbilitiesPanel`
в `hud.tscn`) показывает не полный список действий игры, а то, что риг умеет
ПРЯМО СЕЙЧАС — тем же приёмом, что подсказка взаимодействия (`hud_prompt.gd`):
реагирует на `component_added`/`component_removed` мира, а не поллит каждый
кадр (набор возможностей — дискретное состояние, как у `hud_prompt`, а не
непрерывное число, как у `hud_vitals`).

Скрипт сидит на ПОДЛОЖКЕ (`PanelContainer`), а не на списке строк внутри неё:
`hide()`/`show()` self прячут подложку целиком, а не только текст. Разделитель
между строками — та же логика: виден он ровно тогда, когда строк на экране
две, а не одна (см. [[#Доводка после первого прогона]]).

Две строки:
- **Ход / Полёт** — всегда видна, движение доступно в любом состоянии, меняется
  только его смысл (`C_Flight` на риге → «Полёт», иначе → «Ход»).
- **Прыжок** — только пока на риге есть `C_Jump`; у безногого тела строка
  **пропадает**, а не гаснет серым (в один голос с картой: наличие компонента =
  наличие возможности, полумеры вроде «показать, но неактивным» этой модели
  противоречат). Клавиша резолвится из `InputMap` по `C_Jump.action_name` через
  `SettingsManager.action_display_name()` — тем же приёмом, что подсказка
  взаимодействия читает `C_Interactable.action_name`; после переназначения
  строка обновится сама.

`action_name` добавлен только `C_Jump`: это единственная возможность с ОДНОЙ
дискретной клавишей. Ходьба и полёт читают `move_direction` (четыре клавиши
разом, интерпретируемые по-разному в зависимости от системы), а не одну кнопку,
и `action_name` для них не имеет смысла — показывать их предлагается статичной
строкой-режимом, а не подписанной клавишей.

### Доводка после первого прогона

Живой прогон прошёл; следом добавили подложки под текст (`PanelContainer` за
каждым Label) — и HUD обзавёлся двумя мелкими, но настоящими дефектами:

- **Подложки подсказки и сообщения были видны всегда**, даже без текста внутри:
  `hud_prompt.gd`/`hud_message.gd` прятали свой Label, а обёртка-подложка была
  отдельным узлом без скрипта и своей видимостью не управлялась никем. Пустая
  плашка посреди экрана — не «подсказка скрыта», а «подсказка есть, просто в
  ней ничего не написано», разные вещи для игрока. Правка одна на оба файла:
  **скрипт переехал с Label на саму подложку** (`extends PanelContainer`, Label
  — плейн-ребёнок за `@onready`), и `hide()`/`show() self` теперь прячут
  подложку целиком. `hud_abilities.gd` получил ту же перестановку заодно — три
  файла одного назначения обязаны решать «когда показываться» одним приёмом, а
  не тремя разными.
- **Разделитель между Ход и Прыжок был статичным узлом сцены** — виден всегда,
  в том числе когда строка прыжка спрятана (безногое тело), и торчал сиротой
  под одиноким «Ход». Разделитель — не декорация сама по себе, а знак «строк
  больше одной»; `_render()` теперь прячет и показывает его вместе со строкой
  прыжка одной строкой кода, а не оставляет решать сцене.

Оба случая — один и тот же урок: подложка и разделитель не должны быть
самостоятельными узлами с собственной, никем не управляемой видимостью, если
они существуют РАДИ содержимого, у которого видимость уже посчитана.

**Отклик на недоступное действие** — `S_Jump._swallow` (см. код) отвечает
`C_ScreenMessage` «Этому телу нечем прыгать», но **только если игрок во плоти**
(`entity.has_component(C_Embodied)`). Призраку не отвечают вовсе: по
[[Управление]] подниматься взглядом вместо прыжка — ЗАДУМАННОЕ поведение, а не
урезанная возможность, и текст про «тело» был бы враньём — тела у него как раз
и нет. Ответ на нажатие безногого тела и на нажатие призрака — две разные вещи
не потому, что одну забыли, а потому, что вторая не является багом.

## Как решилась развилка «свои возможности души»

Карточка оставляла выбор открытым: «усыплять» их отдельной базой либо хранить и
восстанавливать, как `C_BodyVisual` хранит `restore_*`. Выбрано **ни то, ни
другое в чистом виде**: возможности снимаются с души (`O_SoulTraits` по
появлению `C_Embodied`), а возвращаются **свежими копиями из сцены души**
(`E_Player.soul_traits()`), а не из заначки.

Заначка не годится ровно по той причине, которой карточка и опасалась:
пересадка тело→тело коалесцирует `remove`+`add` `C_Embodied` в один переезд
архетипа, снятия наблюдатель может не увидеть вовсе, и заначка осталась бы
пустой — душа навсегда без полёта. Нечего хранить — нечему и потеряться.

Отсюда же следует, где возможности души авторятся: в **сцене** `e_player.tscn`
(`component_resources`), а не в `define_components()`. У `C_Flight` есть числа,
тюнить их полагается в инспекторе, и восстановление читает тот самый массив.
Поля `ghost_*` из `RS_GameConfig` удалены — возможность и её числа обязаны лежать
в одном месте.

Наблюдатель, а не вызов из захвата, — потому что воплощают душу **два пути**
(`S_BodySnatch` и `RunManager._restore_embodiment`). Правило, расписанное в
обоих, разъезжается молча; в этой же версии на этом уже обожглись с посадкой
облика.

## Попутно: пересадка не снимала лишнего

Разнос вскрыл дефект, которого модель «возможность = компонент» как раз и не
должна допускать: `_embody` снимал с души характеристики **по списку нового
тела**. Всё, чего у новой плоти нет вовсе, оставалось надетым — пересадка из
ходока в «ползуна» давала **прыгающего безногого**. Теперь снимается всё надетое,
и только потом надевается новое; симметрия с `O_ExpelFromBody` держится тем же
правилом «`C_BodyTrait` + `C_Health`».

## Проверка

`dev/abilities_check.tscn` — 45 headless-проверок: что душа умеет сама, что
приходит с телом, что засыпает во плоти и просыпается при выходе; пересадка
тело→тело (возможности души не теряются, характеристики прошлого тела не
остаются); **оба** входа в воплощение — захват и загрузка сейва; поведение
систем — призрак не падает, во плоти тянет вниз, защёлка прыжка не доживает до
следующего тела, настоящий прыжок с настоящего пола (проверяет заодно и
`deps()`-порядок `S_Gravity` перед `S_Jump`); отклик на недоступное действие
(безногому телу отвечают точным текстом, призраку — нет); HUD-раскладка на всех
трёх переходах (призрак → ходок → безногое тело).

Гонявшая эти проверки версия харнесса нашла и собственный баг: тестовый пол,
положенный вплотную к уровню подошв (`y=0`, та же высота, на которой стоят все
тела), перекрывал `_fits` для ЛЮБОЙ последующей попытки вселения — с тем же
симптомом «тело здесь не поместится», что и настоящий отказ, так что несколько
проверок «прошли», не проверив ничего (ложноположительно: ghost и «пересадка,
провалившаяся по месту» одинаково не несут `C_Jump`). Пол сузили до площадки под
самим тестом. Второй баг — ложный: в мире оставался забытый второй `E_Player` из
проверки восстановления сейва, и HUD, ищущий игрока общим запросом по
`C_PlayerInput` (`ECS.world.query.with_all([C_PlayerInput]).execute_one()`),
недетерминированно находил не того. В настоящей игре второй души не бывает
(`RunManager._spawn_player` проверяет `_get_player() != null`), но тестовый
сценарий обязан убирать за собой сущности, которые больше не нужны, — теперь
убирает.
