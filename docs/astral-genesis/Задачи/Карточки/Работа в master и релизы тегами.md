# Работа в master и релизы тегами

Целевая версия: **v0.7.0** — процесс, его стоит переключить **до** первой
фичи версии: пока ветки `release/v0.7.0` нет, переход ничего не ломает.

## Как сейчас

`feat/*` → PR в `release/vX.Y.Z` → PR релизной ветки в `master` → `release.yml`
коммитит бамп версии прямо в `master`, ставит тег, собирает, публикует
([[Релизы и сборка]]). Неудобства:

- синхронизироваться приходится между релизной веткой и `master`, а фичи ветвятся
  от релизной;
- номер версии надо знать заранее — он в имени ветки.

## Как в Godot

Проверено 24.09 по `git ls-remote`, не по памяти:

- В `godotengine/godot` — `master` и по ветке на минорную версию (`4.5`, `4.6`,
  `4.7`, `3.x`). Теги — только стабильные релизы (`4.7.2-stable`).
- **`dev1`…`dev5`, `beta1`…, `rc1`… — не ветки**, а снапшоты `master`: сборки
  конкретного коммита, опубликованные тегами в отдельном репозитории
  `godotengine/godot-builds` (`4.5-dev1`, `4.5-beta3`, `4.5-rc1`). Поэтому среди
  веток их и нет.
- Все PR идут в `master`. Ветка `4.x` отрезается от `master` ближе к стабильному
  релизу; исправления попадают в неё cherry-pick'ом из `master`, из неё же
  выходят патч-релизы `4.x.y`.

## Решения 24.09

- **Все `feat/fix/docs` PR — в `master`.** `master` всегда самый свежий.
- **Снапшотов `-devN`/`-betaN` нет.** Код пишет один человек — достаточно знать,
  с какого коммита собрана сборка.
- **Защиту `master` не включаем** — по той же причине. Значит, бот может
  по-прежнему коммитить бамп версии прямо в `master` (см. ниже).
- **Планирование версии** — доска `Задачи/vX.Y.Z.md`, как сейчас. Changelog
  релиза — PR между двумя тегами: `gh release create --generate-notes` строит
  его сам.
- **Ветка сопровождения `0.x`** — только по факту, если понадобится патч к
  выпущенной версии, пока в `master` уже идёт следующая.

## Номер версии: три варианта

**А. Проставлять только на время сборки.** Тег `v0.7.0` вешается на обычный
коммит `master`, CI вписывает номер в `project.godot` перед экспортом и ничего не
коммитит.

- ➕ `master` никогда не трогает бот; нет служебных коммитов в истории; защиту
  ветки можно включить в любой момент без исключений.
- ➖ Исходник под тегом хранит **прежний** номер — ровно то, от чего когда-то
  ушли, вешая тег на коммит бампа (v0.4.0: тег есть, а в `project.godot` внутри
  сборки `0.3.0`). Локальная сборка с тега тоже обязана вычислять номер из
  `git describe`, а не читать `project.godot`.
- ➖ Редактор показывает номер прошлого релиза всё время разработки.

**Б. Бот открывает PR с бампом, тег — на его мёрж.**

- ➕ Номер под тегом правильный; работает при включённой защите ветки.
- ➖ Релиз в два шага: запуск → PR → мёрж → тег → сборка.
- ➖ PR, открытый встроенным `GITHUB_TOKEN`, **не запускает другие workflow** —
  ни проверочную сборку, ни релиз на мёрже. Нужен отдельный токен (PAT или
  GitHub App) в секретах, то есть ещё одна вещь, которая протухает.

**В. Кнопка «Run workflow» с номером → бот коммитит бамп в `master` → тег на
коммит бампа → сборка.** ✅ **Рекомендация.**

- ➕ Это уже написано: ветка `workflow_dispatch` в `release.yml` делает ровно это.
  Переход — убрать срабатывание на мёрж `release/v*`, остальное как есть.
- ➕ Номер под тегом правильный, релиз — одно действие.
- ➖ В истории `master` есть коммиты `chore: версия X.Y.Z [skip ci]` — по одному
  на релиз.
- ➖ Несовместим с защитой `master` без исключения для бота — но защиту решено не
  включать. Понадобится — переходить на А, а не на Б.

## Сборка «с какого коммита»

Раз снапшотов нет, нужно видеть коммит у любой сборки, а не только у релизной:

- **Сборка на каждый пуш в `master`**, артефакт помечен коротким хэшем (сейчас
  CI собирает только PR, метка — номер PR).
- **Хэш — в саму игру.** Сейчас игра свой номер не показывает нигде
  (`config/version` читает только `dev/release.ps1`). Строка вида
  `0.7.0+a1b2c3d` в углу главного меню и в отладочном оверлее — и по скриншоту
  бага сразу видно, из какого коммита сборка. Для релиза — просто `0.7.0`.

## Что меняется в репозитории

- `release.yml` — только `workflow_dispatch` (вариант В), без срабатывания на
  мёрж PR; тег и бамп как сейчас.
- `build.yml` — PR в `master` и пуш в `master` (метка — короткий хэш), без
  `release/**`.
- `godot-export/action.yml` / `set_version.sh` — вписывать хэш в `config/version`
  для не-релизных сборок, не коммитя его.
- `dev/release.ps1` — версия из параметра или тега, а не из имени ветки; метка
  не-релизной сборки — хэш.
- Главное меню и отладочный оверлей — строка версии.
- Документация: `CLAUDE.md` (Git conventions, Running/Releases),
  [[Релизы и сборка]], скилл `project-status` — он ищет «доску релизной ветки».
- Старые ветки `release/v0.5.0`, `release/v0.6.0` — удалить (теги остаются).
