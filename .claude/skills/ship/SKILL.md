# Ship: от рабочего дерева до PR в master

Поток правки и его грабли описаны в [Релизы и сборка → Работа с git](../../../docs/astral-genesis/how-to/Релизы%20и%20сборка.md);
здесь — порядок шагов и то, на чём он спотыкался.

1. **Коммиты.** `git status` и diff, разбить на логические коммиты, сообщения —
   скиллом `commit-message`. В индекс — только свои файлы, поимённо: в соседних
   worktree работают другие сессии, а в основном дереве лежат незакоммиченные
   правки пользователя, и `git add -A` унесёт их в чужой коммит. Если две задачи
   правили один файл, промежуточное состояние для первого коммита собирается в
   рабочем дереве (итоговые версии — в бэкап), прогоняется его проверка,
   коммитится, итог возвращается из бэкапа.
2. **Подпись.** Проверять тем `gpg`, который берёт git, а не первым в `PATH`:
   у `gpg` из Git Bash своя пустая связка ключей и ответ «No secret key», хотя
   подпись в порядке.
   ```powershell
   "test" | & (git config gpg.program) --clearsign
   ```
   Повисло или упало — остановиться и спросить пользователя. Подпись не обходить
   (`--no-gpg-sign`, `-c commit.gpgsign=false`).
3. **Пуш.** `git push -u origin HEAD`. Завис LFS — порядок разбора в «Релизы и
   сборка» → «LFS-пуш виснет на Windows».
4. **PR — всегда в master**: релизных веток нет (CLAUDE.md → Git conventions).
   ```bash
   gh pr create --base master --title "…" --body-file <файл>
   ```
   `--fill` годится только для одного коммита: при нескольких он берёт заголовок
   первого. Тело — что и почему, какие проверки прогнаны, и строка атрибуции.
5. **CI.** В приложении Claude (desktop) PR привязывается к сессии (`ccd_pr`:
   `get_status`, при необходимости `bind_pr`), и за CI следит приложение — самому
   не опрашивать. В терминале без приложения — `gh pr checks --watch`. Упало —
   `gh run view <id> --log-failed`; прежде чем чинить, отличить своё от
   пришедшего из master: тот же прогон на чистом `origin/master` во временном
   worktree. Своё — починить отдельным коммитом и пушнуть; чужое — назвать
   пользователю, не чинить молча в этом PR.
6. **Мёрж — только по явной просьбе:** `gh pr merge --merge --delete-branch`.
   Состояние PR — `gh pr view <n> --json state,mergedAt`, не по `gh pr list`.
   Работа шла в worktree — после мёржа убрать его; основное дерево не трогать,
   `git pull` там — только если оно чистое и на master.
